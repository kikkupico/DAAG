Many Copies, Acting as One

When data is stored across multiple copies—or handled by many workers at once—what does it take for the whole system to behave as if there were only a single copy? And who could ever tell the difference?

To find out, we return to the ancient Greek island of Arche, where three trading houses must fill one another's grain requests in the exact order they were truly placed—even when heavy clouds hide the sun.

We find out by checking one question: what must a shared queue promise so that, however many copies or workers stand behind it, callers cannot tell it from a single queue operated one step at a time?

After Maurice P. Herlihy and Jeannette M. Wing, Linearizability: A Correctness Condition for Concurrent Objects, 1990

The rule of the board, stated formally

Write <H for the real-time order of a history H: a <H b when operation a receives its response before operation b is invoked. The board is a FIFO queue: placing a request is Enq, and serving a request is Deq.

A history of requests and servings satisfies the rule of the board (linearizability) if all completed operations—plus whichever still-pending operations have already taken effect—can be placed into a single sequential order such that:

  1. Legal sequential behavior: Every serving (Deq) returns the exact request that a single FIFO queue, executing operations one at a time in that sequence, would return.
  2. One instant per span: Each operation takes its place in the sequence at a single moment between its invocation and its response.
  3. Preserves real-time order: Consequently, any operation that completed before another was invoked appears earlier in the sequence (a <H b implies a precedes b).

Herlihy & Wing 1990, §2.2: a history H is linearizable if, after appending responses to some pending invocations and discarding the rest, it is equivalent to a legal sequential history S that preserves the real-time order <H.

Proof · that if every board is linearizable, the whole system is linearizable (Locality)

For a history H and an object x, write H|x for the subhistory of operations on x, and <H for the real-time order: a <H b when a responds before b is invoked. Claim (Locality, Theorem 1, the "if" direction): if every H|x is linearizable, then H is linearizable.

  1. For each object x, choose a valid linearization order <x of H|x. Define a combined relation < as the transitive closure of the union of all <x together with the real-time order <H.
  2. If < is acyclic (contains no loops), we can extend it to a single total order that preserves every <x (satisfying Demand 1 on each object) and preserves <H (satisfying Demands 2 and 3). Thus, it suffices to prove that < contains no cycle.
  3. Suppose for contradiction that a cycle exists, and choose a cycle e₁ < e₂ < … < en < e₁ of minimal length.
  4. The cycle cannot lie entirely on one object x. Because <x is a strict total order on x, any cycle on x would have to use at least one real-time edge b <H a where a <x b—contradicting the fact that <x respects <H. Thus, the cycle must touch at least two objects.
  5. Relabel the cycle so that e₁ is on object x and e₂ is on another object. Since the step from e₁ to e₂ crosses objects, it must be a real-time edge: e₁ <H e₂ (meaning e₁ finished before e₂ began).
  6. No other operation in the minimal cycle can be on object x. Suppose some ei (for i > 2) is the first operation after e₁ on object x. The edge entering ei crosses objects, so ei−1 <H ei. Furthermore, e₂ must have begun before ei−1 finished (otherwise ei−1 <H e₂, giving a shorter cycle e₂ < … < ei−1 < e₂). Chaining these timestamps gives: e₁ finished before e₂ began, which was before ei−1 finished, which was before ei began. Hence e₁ <H ei, yielding a shorter cycle e₁ < ei < … < en < e₁—a contradiction.
  7. Therefore, the final edge en < e₁ also crosses objects and must be a real-time edge en <H e₁. By the same timestamp chain with i = 1, we get en <H e₂, which produces a shorter cycle e₂ < … < en < e₂. Every case contradicts minimality, proving no cycle exists.∎

A total operation (such as Enq on an unbounded queue) is defined in every object state. Claim (Nonblocking property, Theorem 2): if H is linearizable and p is a pending invocation of a total operation in H, then there exists a response r such that H extended by r is also linearizable.

  2. If S already includes the pending invocation p along with some response r, then returning r right now is valid and witnessed by the exact same S.

The busy board, stated formally

Herlihy and Wing's concurrent lock-free queue (§4.2). The board is represented by an unbounded array items initialized to null and a counter back initialized to 1; array slots are never reused.

  1. To enter a request (Enq(x)): Atomically read the current slot index at the peg and increment it by 1 (i := INC(q.back)), then store the request tablet in that slot (STORE(q.items[i], x)).
  2. To serve a request (Deq()): Read the peg's current position (range := READ(q.back) - 1). Scan slots 1 through range in ascending order, atomically swapping each slot with null (SWAP(q.items[i], null)), and return the first non-null tablet found. If all scanned slots are empty, repeat from the beginning.

Proof · that the busy board is linearizable, in outline

Let A: REP → 2ABS map each state r of the array and peg to the set of abstract FIFO queues it could represent: namely, all permutations of the tablets currently in slots that respect the partial order x <r y (where the STORE of x preceded the INC of y). Let Lin(H|ABS) be the set of abstract queue states reachable by valid linearizations of the history so far. Claim (§4.3.2, Theorem 17): for every reachable state r, A(r) ⊆ Lin(H|ABS).

  1. Base case: Initially the board is empty, representing only the empty queue, which belongs to Lin(H|ABS). We show by induction that every step preserves A(r) ⊆ Lin(H|ABS).
  2. Invocations, responses, INC, and READ: None of these steps adds or removes a tablet from a slot, so A(r) is unchanged (or constrained only in ways consistent with the ongoing operation spans).
  3. Placing a tablet (STORE of x): For another tablet y to be required to follow x (x <r y), y's INC would have to occur after x's STORE—which is happening right now. Thus x is maximal in <r and can be appended to the back of any sequence, matching a legal Enq(x) taking effect right now.
  4. Taking a tablet (SWAP of x at slot i): Suppose the loader scans upward from slot 1 and takes x from slot i. Could some other remaining tablet z satisfy z <r x? If so, z's STORE preceded x's INC, which implies both that z sits in a lower slot (j < i) and that z was already in slot j before the loader began scanning. But then the loader would have encountered and taken z before ever reaching slot i! Thus x is minimal in <r and stands first in at least one valid sequence, matching a legal Deq() returning x.∎

Boundaries of the guarantee

What the rule does not sayWhat linearizability does not say

Checking from outside

Proved by design, not by clocks

Liveness

Safety only, not eventual service

Linearizability is a safety property: it forbids wrong answers, but doesn't guarantee that an operation eventually finishes. A shared object is linearizable if every operation appears to take effect at a single instant between its invocation and its response, in an order that respects real time.

Whether backed by one copy or many, each linearizable object can be verified in isolation, and no caller is forced to wait when an operation is always defined.

The paper behind this book

The paper behind this book. Maurice P. Herlihy and Jeannette M. Wing, Linearizability: A Correctness Condition for Concurrent Objects. ACM Transactions on Programming Languages and Systems 12, 3 (July 1990), 463–492. Covers the definition of linearizability, locality (Theorem 1), the nonblocking property (Theorem 2), the comparison with sequential consistency and serializability, the proof method using set-valued abstraction functions, and the lock-free concurrent queue.

The ideas. Herlihy and Wing propose that a concurrent object is correct if every operation appears to take effect instantaneously at some single moment between its invocation and its response. That ensures the object behaves like a single copy executing operations one at a time, while respecting real-time order: any operation that finishes before another begins must take effect first. Because linearizability is defined purely in terms of external calls and responses, clients cannot tell whether an object is implemented by a single copy, replicated across machines, or shared without locks.

Crucially, real-time order is distinct from Lamport's causal order. One operation can finish before another starts without any system message passing between them (as when information travels out-of-band, like our goatherd), and conversely, two operations linked by a message can still overlap in real time. Neither ordering contains the other.

Two properties make linearizability ideal for building modular systems: it is local (a system is linearizable if and only if each individual object is linearizable) and nonblocking (a pending total operation is never forced to wait for another operation). Dropping the real-time requirement gives sequential consistency, which loses locality; applying the one-at-a-time requirement to multi-operation transactions gives serializability, which loses both locality and the nonblocking property.

Finally, when concurrent races make it impossible to point to a single line of code as an operation's linearization point—as in Herlihy and Wing's lock-free queue—we can still prove linearizability by mapping each concrete state to the set of abstract queue orders it could represent, and showing that every such order is valid.
