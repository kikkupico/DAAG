What You Can Promise Alone

When a machine cannot stop to check with other replicas on every transaction, what guarantees can it still keep on its own? Can it hide half-made changes? Show a reply only after the message it answers? Prevent two people from taking the last item?

We find out by exploring what the librarians of the scholars' coast of Paxos could still promise their readers on days when the couriers between libraries stopped running.

We find out by asking what a replica can still promise its clients when it must always answer: which guarantees it can keep on its own while the network between replicas is partitioned, and which it cannot.

After Peter Bailis, Aaron Davidson, Alan Fekete, Ali Ghodsi, Joseph M. Hellerstein and Ion Stoica, Highly Available Transactions: Virtues and Limitations, 2014

A second, smaller promise

Proof · that Read Uncommitted and Read Committed are achievable with high availability

High availability: every client that can reach a non-failing replica gets a response, without that replica contacting any other. Read Uncommitted (Adya's PL-1) forbids G0: a cycle in the graph with an edge from Ti to Tj when Tj overwrites a write of Ti. Read Committed (PL-2) also forbids reading aborted or intermediate writes (G1a–c). Claim. Both can be provided with high availability.

  1. This is §5.1.1. Read Uncommitted (Adya's PL-1) requires that writes to each object are totally ordered and that the order is consistent across objects: the graph of transactions with an edge from Ti to Tj when Tj overwrites Ti's write must have no cycle (no G0). Mark every write of a transaction with one timestamp unique across transactions (a client's identifier combined with a sequence number) and let each replica apply last-writer-wins by timestamp.
  2. Then for any two transactions T1 and T2 that write to the same two items x and y, all of T1's writes carry the same timestamp, and so does all of T2's; whichever has the larger timestamp wins on both. It cannot happen that wx(1) precedes wx(2) while wy(2) precedes wy(1). No replica contacts any other to decide, so every replica can respond.
  3. Read Committed (PL-2) adds that no transaction reads uncommitted or intermediate versions (Adya's G1a–c). A client buffers its writes until it commits, or sends them to a server that does not reveal them to other readers until it is notified of the commit. Then a reader is never shown a write of a transaction that later aborts, nor an intermediate write.
  4. This provides no recency or monotonicity, and the paper notes it satisfies the implementation-agnostic definition rather than the lock-based behaviour of centralised implementations.∎

Sketch · that Monotonic Atomic View is achievable with high availability

Monotonic Atomic View (MAV): once some effect of a transaction Ti is observed by a transaction Tj, all later reads of Tj observe all of Ti's effects, or later versions. A write is pending stable once every replica for the transaction's final writes has received them. Claim. MAV can be provided with high availability.

  1. This is the algorithm sketched in §5.1.2. MAV requires that once some effect of a transaction Ti is observed by Tj, all later reads of Tj observe all of Ti's effects (or later versions): if Tj reads a version written by Ti, a later read cannot return an earlier version of an item Ti wrote.
  2. Begin with the Read Committed algorithm. Replicas withhold new writes from readers until all replicas for the final writes of the transaction have received them (the writes are pending stable). Each write carries the transaction's single timestamp and the list of items written.
  3. When a client reads an item, the returned timestamp and item list give a lower bound on the versions the client must read for the other items in the list. The client attaches the current bound to each later request.
  4. A replica responds with a write matching the bound or a pending-stable write with a higher timestamp. Each replica holds, per item, the highest pending-stable write and the set of writes not yet pending stable. Since the bound refers only to writes already pending stable, which every replica holds, a replica can always respond, so the algorithm is master-less and operations never block on replica coordination.
  5. The paper gives the full algorithm in its technical report; this is its outline.∎

Proof · that Read Your Writes is not achievable with high availability, and is with sticky availability

Read your writes: whenever a client reads an item after updating it, the read returns the updated value or one that overwrote it. Sticky availability: a client always reaches the same replica, and gets a response whenever it can. wx(1) is a write of 1 to item x, and rx(a) a read of x returning a. Claim. Read your writes cannot be provided with high availability, and is provided with sticky availability.

  1. This is §5.1.3. Read your writes requires that whenever a client reads an item after updating it, the read returns the updated value or one that overwrote it. Consider a client that executes T1 : wx(1) and then T2 : rx(a).
  2. Suppose the client executes T1 against a server partitioned from all others. For transactional availability the server must allow T1 to commit.
  3. If the network topology then changes so that the client can execute T2 only on a different replica, partitioned from the one that executed T1, that replica has no way to learn of wx(1). By transactional availability it must respond, so it either stalls indefinitely, violating availability, or returns a value other than 1 or one that overwrote it, violating read your writes.
  4. If the client remains sticky with the server that executed T1, that server holds the write and the scenario is excluded. So read your writes, and with it PRAM (monotonic reads, monotonic writes and read your writes) and causal consistency, require stickiness and are provided by default in a sticky system.∎

Proof · that Lost Update and Write Skew cannot be prevented with high availability

rx(v) is a read of item x returning v, and wx(v) a write of v to x. Lost Update: T1 reads an item, T2 updates it, and T1 then writes from its original read. Write Skew: the same across several items bound by a constraint. Transactional availability: a transaction that reaches a replica for each of its items eventually commits, or aborts by its own choice. Claim. Neither anomaly can be prevented with high availability.

  1. This is §5.2.1. Lost Update: T1 reads an item, T2 updates the same item, and T1 writes based on its original read, losing T2's update. Take T1 : rx(100) wx(100 + 20 = 120) and T2 : rx(100) wx(100 + 30 = 130), submitted on opposite sides of a network partition.
  2. By transactional availability both must be allowed to commit. Whichever of 120 and 130 a replica then chooses, the state could not have arisen from a serial execution of T1 and T2, since a serial execution gives 150.
  3. To prevent it, one of the transactions must not commit. Each side's server could try to detect that another write occurred, but this requires knowing the version of the latest write to x, which reduces to a requirement for linearizability, provably at odds with high availability by Gilbert and Lynch's proof of the CAP theorem.
  4. Write Skew generalises Lost Update to several items: T1 : ry(0) wx(1) and T2 : rx(0) wy(1), with a constraint that only one of x and y may be 1. Run on opposite sides of a partition, both commit and the constraint is violated, though each would have preserved it in isolation; any prevention needs the same knowledge of the other side and is likewise unavailable.
  5. Hence Snapshot Isolation, Cursor Stability and consistent read (which require preventing Lost Update), and Repeatable Read and one-copy serializability (which require preventing both) are not achievable with high availability.∎

  1. This is §5.2.2. A recency guarantee bounds how out of date a read may be: linearizability (reads return the last completed write), safe and regular register semantics, and any bound such as "no more than five seconds out of date".
  2. Let a write complete at a replica on one side of a partition and let a client then read the item at a replica on the other side. The partition may last indefinitely, with no message crossing.
  3. By availability the reading replica must respond, and it can respond only from information it received before the partition began, which does not include the write. So the response is out of date by at least the time the partition has lasted.
  4. Since the partition can last longer than any fixed bound, no recency bound is enforceable. This is the argument of Gilbert and Lynch for the CAP theorem, applied to every recency guarantee.∎

Setting The Scholars' Coast

The paper behind this book

Peter Bailis, Aaron Davidson, Alan Fekete, Ali Ghodsi, Joseph M. Hellerstein and Ion Stoica, Highly Available Transactions: Virtues and Limitations. Proceedings of the VLDB Endowment, Vol. 7, No. 3 (40th International Conference on Very Large Data Bases, Hangzhou, September 2014), 181–192. — A taxonomy of highly available, sticky available and unavailable isolation and consistency models, with proofs of unavailability and proof-of-concept algorithms.

The ideas, plainly.

Bailis and co-authors ask which of the guarantees that databases and distributed systems offer can be kept by a replica that must always answer, even when it is cut off from every other replica for as long as the cut lasts. They call such systems highly available, and with transactions, highly available transactions. They go through the known guarantees and sort them into those that can be kept, those that can be kept if each client stays with one replica, and those that cannot.

The first group includes read committed, which stops a client reading writes that are not finished, monotonic atomic view, which makes the writes of one transaction visible all together or not at all, repeatable reads within a transaction, and monotonic reads and writes and writes-follow-reads. The second adds read-your-writes, PRAM and causal consistency. Each is built by holding writes back from readers until it is safe to show them, never by making a reader wait.

The third group is made of the guarantees that need a replica to know about concurrent operations elsewhere: preventing lost update and write skew, which rules out snapshot isolation, repeatable read in its other senses and serializability, and any bound on how out of date a read may be. These are fundamental, not weaknesses of particular systems. The paper concludes that many applications can live with the first two groups, that some operations will need the third and should use it sparingly, and that high availability buys the lowest delay.

The paper has six authors, Peter Bailis, Aaron Davidson, Alan Fekete, Ali Ghodsi, Joseph M. Hellerstein and Ion Stoica, and all are credited here. Nobody in this telling is named; the librarians and readers are told apart by what they do.
