Changes That Never Clash

Can updates made independently at different machines be combined in any order, any number of times, and always produce the exact same state everywhere—without anyone ever stopping to coordinate?

We find out by exploring how the libraries of the scholars' coast kept count of the scrolls one visiting scholar had out against a single deposit, without ever meeting to settle it.

We find out by working with the idea directly: replicas that accept updates at once, without asking first, and merge their states in any order, any number of times, to the same result.

After Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, Conflict-free Replicated Data Types, 2011 · the same authors, A Comprehensive Study of Convergent and Commutative Replicated Data Types, 2011

Proof · that the state-based counter is a CvRDT, and that every pair of replicas converges

The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is the entry-by-entry maximum. A CvRDT is an object whose states form a semilattice under an order ≤, whose merge ⊔ is the least upper bound, and whose updates never decrease the state. Claim. This counter is a CvRDT, and any two replicas that keep exchanging states converge.

Proof · that every SEC state-based object can be emulated by an op-based one, and conversely

SEC is strong eventual consistency. A state-based object, a CvRDT, is (S, ≤, s0, q, u, m): states, their order, the initial state, query, update and merge. An operation-based object, a CmRDT, is (S, s0, q, t, u, P): states, initial state, query, prepare-update, effect-update and delivery precondition. Claim. Each can emulate the other.

  1. This is Theorems 3 and 4 of the short paper (§3.2).
  2. State-based by op-based. Given a CvRDT (S, ≤, s0, q, u, m), define a CmRDT with the same state and query. Its prepare-update t(a) records s′ = s • u(a) and its effect-update u′(s′) is s • m(s′), delivered to every replica with no precondition. Merge always commutes, so these effect-updates commute, and with reliable delivery the object is a CmRDT.
  3. Op-based by state-based. Given a CmRDT (S, s0, q, t, u, P), take the state (sm, M, D), where sm is the CmRDT's state and M, D are add-only sets of the updates known and the updates delivered. Order (sm, M, D) ≤ (sm′, M′, D′) by M ⊆ M′ ∧ D ⊆ D′.
  4. A local update runs t and u and adds the update to M. A recursive function d delivers any known update in M \ D whose precondition P holds, adds it to D and applies it to sm, until none is enabled. The merge takes the union of the M sets, then runs d.
  5. Every update is delivered exactly once to the embedded object, in an order satisfying P, and the triple forms a monotonic semilattice (the merge is a union, hence a least upper bound). So the emulation is a CvRDT, and it is SEC because the embedded CmRDT is.∎

    Why giving up a single global order is a bargain

    Putting concurrent operations into a single global sequence requires consensus—which, as we saw on Mount Phyle,* cannot tolerate even half the replicas going silent or being cut off. By giving up a single global sequence and requiring only that concurrent operations merge deterministically, CRDTs stay `100%` available for both reads and writes even when all but one library is silent or cut off.Putting concurrent operations into a single global sequence requires consensus—which cannot tolerate even half the replicas becoming unreachable.* By giving up a single global sequence and requiring only that concurrent operations merge deterministically, CRDTs stay `100%` available for both reads and writes even when all but one replica is unreachable.

    Proof · that SEC and sequential consistency are incomparable

    SEC is strong eventual consistency: replicas that have delivered the same updates have the same state. Sequential consistency asks that the result be that of all updates executed in some single order. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), where ∥ means concurrent, e ∈ S. Claim. Neither property implies the other.

    1. This is §3.3 of the short paper. SEC does not imply sequential consistency. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), e ∈ S. Let replica p0 execute add(e); remove(e′), and concurrently replica p1 execute add(e′); remove(e), and let p3 merge both.
    2. Each remove acts on the add it observed at its own replica, and concurrent with the other replica's add, so by the add-wins specification the final state at p3 satisfies e ∈ S ∧ e′ ∈ S.
    3. In any sequentially consistent execution of the four updates in a single order, either remove(e) or remove(e′) is last, and that element is not in S. So the final state above occurs in no sequentially consistent execution.
    4. Sequential consistency does not imply SEC. In the absence of crashes a sequentially consistent object is SEC, since there is a single order after which all replicas terminate in the same state. In general, however, sequential consistency requires consensus, which cannot be solved in the presence of n − 1 crashes, whereas a SEC object is available and converges with up to n − 1 crashes. Therefore the two are incomparable.∎

    The ideas, plainly.

    Shapiro and co-authors ask when replicas of some data can accept changes without ever talking to one another first, and still end the same. Their answer, strong eventual consistency, asks only that replicas that have received the same updates are in the same state. They give two sufficient conditions. In the state-based form the states are ordered so that each update moves a state upward and merging two states is their least upper bound; then merging commutes, groups freely and may be repeated. In the operation-based form every pair of concurrent operations commutes and operations are delivered once each, in causal order. Each form can imitate the other.

    A counter that only counts up is a vector with one entry per replica and a per-entry maximum for merge; a counter that also counts down is two of them. A register can keep the later write or keep both. A set that only grows is a union; a set that also loses elements can let removal win, or let adds win by tagging every add and having a removal take away only the tags it has seen. These all converge, and each means something different by a clash.

    What the approach does not do is keep a rule that spans all the replicas, such as a count that never goes below zero; for that, replicas must agree. It does not decide which meaning of a clash is right, and it is not the same as keeping one order of all the updates: it permits results no single order would give, and it is available where one order would need agreement.

    The papers have four authors, Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, and all are credited here. No one in the book is named: the libraries go by number, and the scholar is the one who lodged the deposit.
