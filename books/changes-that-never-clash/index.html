Changes That Never Clash

Can some changes be combined in any order, any number of times, and still come out the same everywhere, so that they never clash and no one ever needs to coordinate?

We find out by exploring how the libraries of the scholars' coast keep one compendium of knowledge, each changing its own copy at once and merging the copies the couriers bring, without ever meeting to settle anything.

We find out by working with the idea directly: replicas that accept updates at once, without asking first, and merge their states in any order, any number of times, to the same result.

After Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, Conflict-free Replicated Data Types, 2011 · the same authors, A Comprehensive Study of Convergent and Commutative Replicated Data Types, 2011

Proof · that the state-based counter is a CvRDT, and that every pair of replicas converges

The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is the entry-by-entry maximum. A CvRDT is an object whose states form a semilattice under an order ≤, whose merge ⊔ is the least upper bound, and whose updates never decrease the state. Claim. This counter is a CvRDT, and any two replicas that keep exchanging states converge.

  1. This is Specification 6 of the comprehensive report (the G-Counter). The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is Z with Z.P[i] = max(X.P[i], Y.P[i]) for each i.
  2. The order is X ≤ Y ⇔ ∀i, X.P[i] ≤ Y.P[i]. Componentwise maximum is the least upper bound of two vectors under this order, since it is an upper bound of both and any other upper bound is at least as large in every entry. So the states form a semilattice, and merge is its join.
  3. Each update increases one entry and leaves the rest, so the state never decreases: s ≤ s • increment. The object is a monotonic semilattice, hence a CvRDT (Theorem 1 of the short paper).
  4. Now let xi and xj be any two replicas that can exchange states infinitely often by some channel that eventually delivers (Proposition 2.1 of the report). Let xi′ = xi ⊔ xj and xj′ = xj ⊔ xi. By the commutativity of ⊔, xi′ = xj′, and by idempotence and associativity further merges of the same states change nothing. Both replicas have the same causal history, C(xi) ∪ C(xj), and the same state.
  5. The report states two assumptions of this vector form: the payload does not overflow, and the set of replicas is known. A grow-only set of unique tags, one per increment, can serve as the same counter without knowing the replicas.∎

Proof · that every SEC state-based object can be emulated by an op-based one, and conversely

SEC is strong eventual consistency. A state-based object, a CvRDT, is (S, ≤, s0, q, u, m): states, their order, the initial state, query, update and merge. An operation-based object, a CmRDT, is (S, s0, q, t, u, P): states, initial state, query, prepare-update, effect-update and delivery precondition. Claim. Each can emulate the other.

  1. This is Theorems 3 and 4 of the short paper (§3.2).
  2. State-based by op-based. Given a CvRDT (S, ≤, s0, q, u, m), define a CmRDT with the same state and query. Its prepare-update t(a) records s′ = s • u(a) and its effect-update u′(s′) is s • m(s′), delivered to every replica with no precondition. Merge always commutes, so these effect-updates commute, and with reliable delivery the object is a CmRDT.
  3. Op-based by state-based. Given a CmRDT (S, s0, q, t, u, P), take the state (sm, M, D), where sm is the CmRDT's state and M, D are add-only sets of the updates known and the updates delivered. Order (sm, M, D) ≤ (sm′, M′, D′) by M ⊆ M′ ∧ D ⊆ D′.
  4. A local update runs t and u and adds the update to M. A recursive function d delivers any known update in M \ D whose precondition P holds, adds it to D and applies it to sm, until none is enabled. The merge takes the union of the M sets, then runs d.
  5. Every update is delivered exactly once to the embedded object, in an order satisfying P, and the triple forms a monotonic semilattice (the merge is a union, hence a least upper bound). So the emulation is a CvRDT, and it is SEC because the embedded CmRDT is.∎

One compendium from its partsA map of CRDTs

An entry is its parts side by side. One copy of an entry is ahead of another when every part is ahead: as many pebbles or more in every column, an account written after the other's, every tag the other has. Merging two copies merges each part by its own rule, so the whole entry merges in any order and any number of times as well.A composite value is a tuple of CRDTs. One state is below another when every component is below; the merge is the merge of each component. A product of semilattices is a semilattice, so the composite is itself a CRDT.

The headings work like the references: a list in which every writing has its own tag. Writing anything into an entry writes a fresh tag on its heading. Withdrawing a heading strikes the tags the withdrawing library can see, and the entry is hidden while no tag of its heading stands; its parts are kept, and merged like any others.The keys work like the set: an add-wins set in which every update to a value adds a fresh tag to its key. Removing a key removes the tags the remover has observed, and the value is hidden while no tag remains; its components are kept and merged as before.

Proof · that a value made of CRDT parts, and a map of such values with add-wins keys, is a CRDT

Let (S1, ≤1, ⊔1), …, (Sk, ≤k, ⊔k) be the states of k CvRDTs, each a monotonic semilattice. Their product is S = S1 × … × Sk, ordered and merged componentwise; an update applies an update of one component. A map adds an OR-Set of pairs (κ, uid) beside a product value for every key κ. Claim. The product is a CvRDT, and so is the map.

  1. The short paper states that CRDT types can be composed, and the report builds its PN-Counter as two G-Counters side by side (Specification 7) and its shopping cart as a map on an OR-Set (§5). The general argument below is this book's; the papers give no separate theorem for it.
  2. Order x ≤ y ⇔ ∀j, xj ≤j yj. The componentwise merge x ⊔ y = (x1 ⊔1 y1, …, xk ⊔k yk) is an upper bound of x and y, and any upper bound z has zj ≥j xj ⊔j yj in every component, since each ⊔j is a least upper bound. So S is a semilattice and ⊔ is its join.
  3. An update of component j moves xj up in ≤j and leaves the others, so it moves x up in ≤. The product is a monotonic semilattice, hence a CvRDT (Theorem 1 of the short paper).
  4. For the map, the state is the product of an OR-Set of pairs (κ, uid) and a value for every key, each value a product as above. An update to the value under κ also adds a fresh pair (κ, uid); a removal of κ removes the pairs (κ, uid) it observed. Key κ is present while some pair (κ, uid) is added and not removed. The OR-Set is a CRDT (report, Specification 15), and the values are kept whether or not κ is present, so the map is again a product of CRDTs.
  5. As the report argues for its map (§5, the OR-Cart): two adds commute, since each pair is unique; two removes commute, since the downstream set-minus operations are either independent or idempotent; and an add is independent of a concurrent remove, since its pair is unique. So a key updated concurrently with its removal remains present. Nothing in either component's merge reads the other, so an invariant relating two components is not preserved by merging.∎
Something different in kind

Not the same as one order

On Arche, every copy behaves as if all changes across the island had been made one at a time in a single order: sequential consistency.* The libraries' guarantee, that copies which have taken in the same changes are the same (strong eventual consistency, SEC), is a different promise.We have also met sequential consistency:* every replica behaves as if all operations were executed in a single global sequence. Strong eventual consistency (SEC), that replicas which have received the same updates are in the same state, is a different promise.

Take the comet's list of references, with a tag for every writing. In the same hour Library 1 adds a reference to the entry on eclipses (E) and then strikes the reference to falling stars (F), while Library 2 adds F and then strikes E. When both lists reach Library 3, each strike saw nothing of the other library's adding, so both E and F stand.Take a tagged set (OR-Set). Concurrently, Replica 1 adds element E and then removes F, while Replica 2 adds F and then removes E. When both states merge at a third replica, each remove observed nothing of the other replica's add, so both E and F are in the set.

Arranged in any single order, one at a time, whichever strike came last would remove its reference and leave at most one. So the libraries can agree on a list that no single order of the four changes could produce.Arranged in any single sequence, whichever remove came last would remove its element and leave at most one. So CRDTs can converge to a state that no sequential execution produces.

    Neither contains the other

    Why giving up a single order is a bargain

    Putting every change into one order needs the libraries to agree, and agreement stops when too many of those who must agree fall silent.* Giving up one order, and asking only that changes merge the same everywhere, lets every library read and change its copy even when all the others are cut off.Putting every operation into one sequence needs consensus, which cannot be solved when too many replicas crash or become unreachable.* Giving up one sequence, and asking only that concurrent operations merge deterministically, keeps every replica available for reads and writes even when all the others are unreachable.

    The parts give the libraries an entry they can always read and change at their own desks, merged by rules alone. Some things those rules do not give.The components give each replica a value it can always read and update locally, merged by rules alone. Some things those rules do not give.

    Proof · that SEC and sequential consistency are incomparable

    SEC is strong eventual consistency: replicas that have delivered the same updates have the same state. Sequential consistency asks that the result be that of all updates executed in some single order. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), where ∥ means concurrent, e ∈ S. Claim. Neither property implies the other.

    1. This is §3.3 of the short paper. SEC does not imply sequential consistency. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), e ∈ S. Let replica p0 execute add(e); remove(e′), and concurrently replica p1 execute add(e′); remove(e), and let p3 merge both.
    2. Each remove acts on the add it observed at its own replica, and concurrent with the other replica's add, so by the add-wins specification the final state at p3 satisfies e ∈ S ∧ e′ ∈ S.
    3. In any sequentially consistent execution of the four updates in a single order, either remove(e) or remove(e′) is last, and that element is not in S. So the final state above occurs in no sequentially consistent execution.
    4. Sequential consistency does not imply SEC. In the absence of crashes a sequentially consistent object is SEC, since there is a single order after which all replicas terminate in the same state. In general, however, sequential consistency requires consensus, which cannot be solved in the presence of n − 1 crashes, whereas a SEC object is available and converges with up to n − 1 crashes. Therefore the two are incomparable.∎

INRIA Research Report RR-7506, January 2011. — The portfolio: counters, registers, sets, graphs, sequences, with specifications and proofs, and a shopping cart built from them.

    The ideas, plainly.

    Shapiro and co-authors ask when replicas of some data can accept changes without ever talking to one another first, and still end the same. Their answer, strong eventual consistency, asks only that replicas that have received the same updates are in the same state. They give two sufficient conditions. In the state-based form the states are ordered so that each update moves a state upward and merging two states is their least upper bound; then merging commutes, groups freely and may be repeated. In the operation-based form every pair of concurrent operations commutes and operations are delivered once each, in causal order. Each form can imitate the other.

    A counter that only counts up is a vector with one entry per replica and a per-entry maximum for merge; a counter that also counts down is two of them. A register can keep the later write or keep both. A set that only grows is a union; a set that also loses elements can let removal win, or let adds win by tagging every add and having a removal take away only the tags it has seen. Such types can be put side by side and merged part by part, and a map keeps one under every key. These all converge, and each means something different by a clash.

    What the approach does not do is keep a rule that spans all the replicas, such as a count that never goes below zero, or a rule that joins two parts; for that, replicas must agree, or hand out rights in advance. It does not decide which meaning of a clash is right, and it is not the same as keeping one order of all the updates: it permits results no single order would give, and it is available where one order would need agreement.

    The papers have four authors, Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, and all are credited here. No one in the book is named: the libraries go by number.
