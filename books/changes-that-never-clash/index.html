Changes That Never Clash

Can updates made independently at different machines be combined in any order, any number of times, and always produce the exact same state everywhere—without anyone ever stopping to coordinate?

We find out by exploring how scribes on the far southern terraces of Paxos kept a shared count of books in grooves of pebbles that always merged to the same answer.

First, in machine terms

Replicas that never ask first

Suppose several replicas hold copies of the same data object. Each replica accepts updates locally and immediately, without asking any other replica first, and the replicas exchange their states or operations in the background.

  • Strong Eventual Consistency (SEC): any two replicas that have received the same set of updates—in whatever order—are guaranteed to be in the exact same state immediately, with no rollbacks and no consensus.
  • State-based (`CvRDT`) and Operation-based (`CmRDT`): in the state-based form, states form a monotonic semilattice where updates only move the state upward and merging two states takes their least upper bound (which is commutative, associative, and idempotent). In the operation-based form, concurrent operations commute.
  • Conflict-Free Replicated Data Types (CRDTs) (Shapiro et al., 2011) show how to build counters, registers, sets, and graphs that satisfy these rules—and prove what kinds of invariants cannot be maintained without coordination.

We tell this story on the far southern terraces of Paxos, where scribes keep the coast's counts in grooves of pebbles on stone tables.

The far terraces

A table of pebbles on every terrace

At the southern tip of Paxos, as far from the Chamber and the Tholos as the island goes, a hillside above the sea is cut into three stone terraces. On each terrace sits a grooved marble counting table where a scribe tracks how many copies of each work have been made on the coast.*

No waitingWhenever a copy is made at the library nearest him, a scribe adds a pebble to his table immediately, without asking the other terraces.
Tables by courierThe terraces send copies of their tables to one another by courier. A courier may arrive late, out of order, or twice.
The same countAny two terraces that have heard of the same copies must show the exact same total.
What is wanted

The count no one settles

The tables on the three terraces count how many copies of a work have been made, using pebbles (`psēphoi`) laid in grooves on a stone slab. The scribe of the first terrace is Shapirios.

Suppose at first that each table kept only a single pile of pebbles for the work. Now watch what goes wrong when Terrace 1 and Terrace 2 each make one new copy of the work at the same time: each scribe puts one pebble on his own table, so both tables show `1` even though `2` copies were actually made.

When a courier carries Terrace 1's count (`1`) to Terrace 2 (`1`), how should Terrace 2 combine them? If it keeps the larger of the two numbers (`max(1, 1) = 1`), one of the two copies vanishes from the count forever. If instead it adds the two numbers (`1 + 1 = 2`), the count is right this once—until a second courier arrives with the table again, or the two terraces exchange tables a second time (`2 + 2 = 4`), inflating the count endlessly on copies that were made only once!

The scribes could avoid this by taking turns or holding a vote before adding a pebble, as the assemblies in the north do—but then every stopped courier would freeze the tables. What Shapirios wants is a way to add pebbles immediately, merge tables in any order and any number of times, and always land on the true count.

One writer to a column

One column each

Why did a single pile fail? Because two different scribes were adding pebbles to the same pile, making it impossible to tell a new pebble from one already counted.

The cure is to carve a separate column (`groove`) on every table for each of the three terraces—just like the column rooms of Arche.* When a copy is made at Terrace 1, Shapirios adds a white pebble only to Column 1. The scribe at Terrace 2 adds pebbles only to Column 2, and the scribe at Terrace 3 adds pebbles only to Column 3.

Now each column has only a single writer, and each column only ever grows. On any terrace's table, Column i records how many copies Terrace i has made according to the latest news that has reached this table. And the total number of copies made across the coast is simply the sum of all three columns.

When two tables meet

Take the larger

When a courier brings another terrace's table, the receiving scribe compares the incoming table with his own column by column, and in each column he keeps the larger pile (`max`).

Why does taking the larger pile in each column never lose a pebble and never double-count one? Because only Terrace i ever adds pebbles to Column i! In Column i, a pile of `4` pebbles is not a separate set of copies from a pile of `3` pebbles; it is the exact same `3` copies plus `1` newer copy. Taking the larger pile in each column therefore satisfies three golden laws:

• Order does not matter (`commutative`): merging Table A into Table B gives the exact same result as merging Table B into Table A.
• Grouping does not matter (`associative`): merging A with B and then C gives the same result as merging B with C and then A.
• Repetition does not matter (`idempotent`): merging the same table a second or third time changes nothing at all.

Why adding the totals is wrong

Two tables each hold part of the same piles

If two tables both know about the first two copies made at Terrace 1, adding their columns would count those two pebbles twice—and would count them again at every subsequent meeting. Taking the maximum in each column counts every pebble once, no matter how many times or by how many paths the tables meet.

Notice how little this requires from the world: even if couriers between Terrace 1 and Terrace 2 are completely stopped, both terraces can keep adding pebbles and answering readers, and as soon as a single courier eventually gets through in each direction, their tables converge to the exact same state.

Proof · that the state-based counter is a CvRDT, and that every pair of replicas converges

The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is the entry-by-entry maximum. A CvRDT is an object whose states form a semilattice under an order ≤, whose merge ⊔ is the least upper bound, and whose updates never decrease the state. Claim. This counter is a CvRDT, and any two replicas that keep exchanging states converge.

  1. This is Specification 6 of the comprehensive report (the G-Counter). The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is Z with Z.P[i] = max(X.P[i], Y.P[i]) for each i.
  2. The order is X ≤ Y ⇔ ∀i, X.P[i] ≤ Y.P[i]. Componentwise maximum is the least upper bound of two vectors under this order, since it is an upper bound of both and any other upper bound is at least as large in every entry. So the states form a semilattice, and merge is its join.
  3. Each update increases one entry and leaves the rest, so the state never decreases: s ≤ s • increment. The object is a monotonic semilattice, hence a CvRDT (Theorem 1 of the short paper).
  4. Now let xi and xj be any two replicas that can exchange states infinitely often by some channel that eventually delivers (Proposition 2.1 of the report). Let xi′ = xi ⊔ xj and xj′ = xj ⊔ xi. By the commutativity of ⊔, xi′ = xj′, and by idempotence and associativity further merges of the same states change nothing. Both replicas have the same causal history, C(xi) ∪ C(xj), and the same state.
  5. The report states two assumptions of this vector form: the payload does not overflow, and the set of replicas is known. A grow-only set of unique tags, one per increment, can serve as the same counter without knowing the replicas.∎
What a courier carries

Sending the table or the change

There are two ways for terraces to share updates: a courier can carry a copy of the terrace's entire table (the table way, or state-based `CvRDT`), or a short slip announcing just the single operation add one pebble for Terrace 1 (the notice way, or operation-based `CmRDT`).

Both approaches reach the exact same state, but they place very different demands on the couriers.

Terrace 1 has one more copy to report send it either way, as often as you like

1copies made0shown at terrace 2

Terrace 2 has not heard yet.

What the table way asks

Almost nothing

Because merging two tables by taking the larger pile is idempotent, a courier carrying a whole table can arrive twice, arrive out of order, or be lost completely (as long as some later table gets through), and the count is still right. The only downside is size: carrying the entire table just to report one new pebble.

What the notice way asks

Exactly once, in causal order

Adding one pebble commutes with adding another pebble, so notices from different terraces can arrive in any order. However, applying the same notice twice counts the copy twice, and losing a notice loses the copy forever! For general operation-based CRDTs, the delivery channel must deliver every notice exactly once and in causal order (so a removal notice never arrives before the addition it removes).

Each is the other in disguise

A table as a notice, notices in a table

Mathematically, the two forms are equivalent: any state-based CRDT can be turned into an op-based one by sending its state as an operation (`merge this state`), and any op-based CRDT can be turned into a state-based one by keeping the set of known and delivered notices as part of the table.

Proof · that every SEC state-based object can be emulated by an op-based one, and conversely

SEC is strong eventual consistency. A state-based object, a CvRDT, is (S, ≤, s0, q, u, m): states, their order, the initial state, query, update and merge. An operation-based object, a CmRDT, is (S, s0, q, t, u, P): states, initial state, query, prepare-update, effect-update and delivery precondition. Claim. Each can emulate the other.

  1. This is Theorems 3 and 4 of the short paper (§3.2).
  2. State-based by op-based. Given a CvRDT (S, ≤, s0, q, u, m), define a CmRDT with the same state and query. Its prepare-update t(a) records s′ = s • u(a) and its effect-update u′(s′) is s • m(s′), delivered to every replica with no precondition. Merge always commutes, so these effect-updates commute, and with reliable delivery the object is a CmRDT.
  3. Op-based by state-based. Given a CmRDT (S, s0, q, t, u, P), take the state (sm, M, D), where sm is the CmRDT's state and M, D are add-only sets of the updates known and the updates delivered. Order (sm, M, D) ≤ (sm′, M′, D′) by M ⊆ M′ ∧ D ⊆ D′.
  4. A local update runs t and u and adds the update to M. A recursive function d delivers any known update in M \ D whose precondition P holds, adds it to D and applies it to sm, until none is enabled. The merge takes the union of the M sets, then runs d.
  5. Every update is delivered exactly once to the embedded object, in an order satisfying P, and the triple forms a monotonic semilattice (the merge is a union, hence a least upper bound). So the emulation is a CvRDT, and it is SEC because the embedded CmRDT is.∎

Whether a system sends full states or individual notices is therefore a practical trade-off between message size and channel bookkeeping, not a difference in what can be computed.

A count that goes down

Made and lost

Taking the larger pile in each column works because a column only ever grows. What if copies can also be lost or worn out, so the total count of surviving copies has to go down?

If a scribe simply took a white pebble out of his column when a copy was lost, the very next table arriving from another terrace—which still remembers the larger pile—would put that white pebble right back! Just as with withdrawing a work in Spreading by Word of Mouth, a subtraction cannot travel as a missing pebble.

Instead, each table is carved with two sets of three columns (`PN-Counter`): three columns of white pebbles for copies made, and three columns of black pebbles for copies lost. When a copy is lost at Terrace i, its scribe adds a black pebble to his own black column. Both the white columns and the black columns only ever grow, so both merge cleanly by taking the larger pile in each column—while the net number of surviving copies (white total minus black total) can go either up or down!

One copy left, two scribes each sees one copy on the table before them

A scribe may mark a copy lost

The one copy was made at terrace 1. Both tables show it.

The first thing the idea cannot do

A global floor—such as “the total count must never go below zero”—cannot be enforced locally

Suppose only `1` copy remains on the coast, and both Terrace 1 and Terrace 2 see `1` on their tables. If each scribe is allowed to mark a copy lost whenever his table shows at least `1`, both scribes can add a black pebble at the same time—and when their tables merge, the count drops to `−1`! A scribe can avoid this only if he restricts himself to a local rule (such as never marking more copies lost than his own terrace made, or pre-allocating a quota of losses by escrow), or if the terraces stop and coordinate before decrementing.

Corrections that meet

Two hands on one work

What if the record being kept is not a count of pebbles, but the text of a work itself (`a register`)? When two libraries revise the same work independently, how can the terraces merge them so that every terrace ends with the exact same result?

Here the mathematics of CRDTs leaves the designer a choice between two different rules—both of which merge in any order and any number of times.

Library 1 writes at noon, Library 2 later that day choose the rule, and the order in which the two corrections reach a terrace

The plain rule

Keep the later (`LWW-Register`)

Attach a unique tally (timestamp plus library number) to each edition, and when two editions meet, keep the one with the larger tally.* Because `max` on timestamps is commutative, associative, and idempotent, every terrace converges—at the price of silently discarding the earlier concurrent edit.

What it needs

Tallies that respect causality

For `keep the later` to make sense when one scholar revises another scholar's edition, the second scholar's tally must be guaranteed to be larger than the first's (for instance, by using Lamport clocks).

The other rule

Keep both (`MV-Register`)

To avoid silently throwing away concurrent work, each edition carries a vector of column counts (`version vector`) showing which editions its writer had already seen. When two tables merge, an edition is replaced only by an edition that causally supersedes it; two concurrent editions are both kept side by side until a scholar reads both and writes a combined edition.

Both rules guarantee that every terrace converges to the same shelf. What separates them is what the designer wants a concurrent clash to mean: pick a winner automatically, or preserve both branches for a human to reconcile.

A list of titles

Titles added and struck

Suppose the terraces also maintain a shared catalogue of titles (`a set`). If titles are only ever added and never removed (`G-Set`), merging two catalogues is just taking their set union (`A ∪ B`), which is automatically commutative, associative, and idempotent.

What if scribes can also strike (remove) a title from the catalogue? If a scribe simply erased a title from his scroll, the next merge with another scroll would union it right back in! And if Library 1 adds a title at the same time Library 2 strikes it, who should win? The paper gives three ways to build a conflict-free set with removals:

The cheap way

A struck-off list (`2P-Set`)

Keep two grow-only lists: an added list and a struck-off list (`tombstone set`). A title is in the catalogue if it is on the added list and not on the struck-off list. Both lists only grow, so both merge by union—but once a title is struck off, it can never be added again!

The way most like an ordinary list

A tag for every writing (`OR-Set`)

Every time a library adds a title, it attaches a fresh, globally unique tag to that entry. A title is in the catalogue as long as at least one of its tags remains un-struck. When a scribe strikes a title, he adds to the struck-off list only the specific tags he can currently see on his table (`observed-remove`).

Other ways

A tally, or a count (`LWW-Set` / `PN-Set`)

Alternatively, each title can carry a timestamp on its latest add and latest strike (`LWW-element-Set`), or a pebble counter incremented on add and decremented on strike (`PN-Set`—though striking a title twice then anomalously requires adding it twice to bring it back!).

One title, two libraries, a tag for every writing add and strike in any order, then let the two exchange

Each library sees only its own list until the two exchange.

A strike takes away only the tags it has seen

When an add and a strike happen in ignorance of each other, the add wins

Why does tagging every writing (`OR-Set`) feel so natural? Because if a title is struck at Library 1 and later re-added, the re-addition gets a brand-new tag that is not on the struck-off list, so the title comes back cleanly. And if Library 1 strikes a title while Library 2 concurrently adds it, Library 1's strike only cancels the old tags it knew about, leaving Library 2's fresh tag—and the title—standing (`add-wins`).

Something different in kind

Not the same as one order

On Arche, we met the looser rule of sequential consistency:* every replica behaves as if all operations across the island were executed in a single global sequence. Does Strong Eventual Consistency (`SEC`) mean the same thing?

No! Watch what happens with our tagged catalogue (`OR-Set`) when two libraries act concurrently: Library 1 adds title E and then strikes title F; at the exact same time, Library 2 adds title F and then strikes title E. When the two lists merge at a terrace, each library's strike saw nothing of the other library's concurrent add, so both E and F remain on the catalogue!

Yet if you tried to arrange those four operations into any single one-at-a-time sequence, whichever operation came fourth (`strike F` or `strike E`) would have to remove its title, leaving at most one title on the list. Thus CRDTs can converge to a state that no single sequential order could ever produce.

    Neither contains the other

    Why giving up a single global order is a bargain

    Putting concurrent operations into a single global sequence requires consensus—which, as we saw on Mount Phyle,* cannot tolerate even half the replicas going silent or being cut off. By giving up a single global sequence and requiring only that concurrent operations merge deterministically, CRDTs stay `100%` available for both reads and writes even when all but one terrace is silent or cut off.

    Proof · that SEC and sequential consistency are incomparable

    SEC is strong eventual consistency: replicas that have delivered the same updates have the same state. Sequential consistency asks that the result be that of all updates executed in some single order. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), where ∥ means concurrent, e ∈ S. Claim. Neither property implies the other.

    1. This is §3.3 of the short paper. SEC does not imply sequential consistency. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), e ∈ S. Let replica p0 execute add(e); remove(e′), and concurrently replica p1 execute add(e′); remove(e), and let p3 merge both.
    2. Each remove acts on the add it observed at its own replica, and concurrent with the other replica's add, so by the add-wins specification the final state at p3 satisfies e ∈ S ∧ e′ ∈ S.
    3. In any sequentially consistent execution of the four updates in a single order, either remove(e) or remove(e′) is last, and that element is not in S. So the final state above occurs in no sequentially consistent execution.
    4. Sequential consistency does not imply SEC. In the absence of crashes a sequentially consistent object is SEC, since there is a single order after which all replicas terminate in the same state. In general, however, sequential consistency requires consensus, which cannot be solved in the presence of n − 1 crashes, whereas a SEC object is available and converges with up to n − 1 crashes. Therefore the two are incomparable.∎
    The limits

    What it does not say

    The terraces get counts, registers, and catalogues that can always be read and updated locally and that converge by merging alone. Here are five things they do not get.

    Does it enforce global limits?

    No. Any invariant that restricts the combined state across replicas—such as a count that must never dip below zero, or two titles that must never appear together—cannot be enforced locally without coordination or pre-allocated escrow quotas.

    Does it decide which clash rule is “right”?

    No. Mathematical convergence guarantees only that every terrace lands on the same answer—whether that answer is `add-wins`, `remove-wins`, `last-writer-wins`, or `keep-both` is a choice the system designer must make for each domain.

    Do the tables stay small on their own?

    Not automatically. A counter has a column for every replica, and sets with removals accumulate tombstones or tags over time. Safely pruning old tombstones requires knowing that every replica has already seen them—which requires background coordination while all replicas are reachable.

    What does it assume?

    It assumes honest scribes (no Byzantine faults): a scribe who tampers with another terrace's column or forges tags can corrupt the state. And for operation-based (`notice-way`) CRDTs, it assumes the messaging layer delivers every notice exactly once in causal order.

    Are counters, registers, and sets the only CRDTs?

    Not at all. The comprehensive report also builds conflict-free directed graphs (such as cross-references between works) and cooperative text-editing sequences (`treedoc` / `RGA`) using the exact same semilattice and commutativity principles.

    The ideas, plainly.

    Shapiro and co-authors ask when replicas of some data can accept changes without ever talking to one another first, and still end the same. Their answer, strong eventual consistency, asks only that replicas that have received the same updates are in the same state. They give two sufficient conditions. In the state-based form the states are ordered so that each update moves a state upward and merging two states is their least upper bound; then merging commutes, groups freely and may be repeated. In the operation-based form every pair of concurrent operations commutes and operations are delivered once each, in causal order. Each form can imitate the other.

    A counter that only counts up is a vector with one entry per replica and a per-entry maximum for merge; a counter that also counts down is two of them. A register can keep the later write or keep both. A set that only grows is a union; a set that also loses elements can let removal win, or let adds win by tagging every add and having a removal take away only the tags it has seen. These all converge, and each means something different by a clash.

    What the approach does not do is keep a rule that spans all the replicas, such as a count that never goes below zero; for that, replicas must agree. It does not decide which meaning of a clash is right, and it is not the same as keeping one order of all the updates: it permits results no single order would give, and it is available where one order would need agreement.
