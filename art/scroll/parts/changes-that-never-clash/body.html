First, in machine terms

Replicas that never ask first

Several replicas hold the same data. Each accepts updates on its own, with no coordination, and the replicas exchange what they have afterwards.

  • Strong eventual consistency: replicas that have received the same updates are in the same state.
  • State-based: merging two states must be commutative, associative and idempotent, and updates must only move a state upward.
  • Conflict-free replicated data types (Shapiro et al., 2011): counters, registers and sets built that way, and what cannot be.

We tell it with pebbles on a marble board at each library's loan desk, counting the scrolls one scholar has out against his deposit.

The loan desks

One deposit, a table at every desk

A visiting scholar reads at the libraries of the scholars' coast. He lodges one deposit, and any library may lend him scrolls against it. Each library keeps a table of pebbles for him on its loan desk, and couriers carry the tables between the libraries.*

No waitingThe desk he stands at lends at once and adds a pebble, without asking anyone.
Tables by courierThe libraries send one another their tables. A courier may be late, lost, or arrive twice.
The same countLibraries that have heard of the same loans must show the same number out.
What is wanted

The count no one settles

When he leaves, every scroll he still has out is paid for from his deposit, so each of the three libraries he uses must be able to say from its own table how many he has out. The table counts in pebbles set in grooves on a marble board. Every desk keeps a board like this for each scholar who has lodged a deposit; we watch only his. Leave returns aside for now: until a scroll comes back, every scroll lent is a scroll out.

Start with one pile for him. Two libraries each lend him a scroll at the same time, each unaware of the other. Each table shows one scroll out, and he has two.

When the tables meet, keeping the larger pile keeps one, and a loan is lost. Adding the two piles gives two, which is right this once. At the next meeting the same piles are added again, and the count rises for ever on scrolls lent once.

The libraries could take turns, but then they wait for one another, and a stopped courier leaves the scholar waiting at the desk. What is wanted is narrower than agreement: add at once, show the same count for the same news in whatever order it came, and never take anything back.

One writer to a column

One column each

The trouble was that two libraries added to the same pile. So each board is cut with a column for every library, and a librarian adds white pebbles only to the column of the librarian's own library.

A column then has one writer, and it only goes up. When two libraries each add a pebble, they add to different columns, and neither can overwrite or double the other. On any table, a column is the number of scrolls its library has lent him, as far as that table has heard. The number he has out is the sum of the columns.

A library learns another's pile by being sent its table. Its own table has its own column up to date and the others as old as the news that has reached it. The table that arrives is out of date in a different way. The library needs a rule for which pile in each column to keep.

When two tables meet

Take the larger

A library keeps the larger pile in each column. A column only ever grows, so of two piles in the same column the larger is the later, and holds everything the smaller holds and more.

Three things are then true of merging, and the whole idea rests on them. It does not matter which table is merged into which. It does not matter how several tables are grouped. And merging the same table twice changes nothing. A table can be lost, delayed, copied, or arrive out of turn, and the library that takes it in ends at the same place.

Why adding the totals is wrong

Two tables each hold part of the same piles

Adding them counts the shared part twice, and again at every later meeting. Taking the larger in each column counts each pile once, because it never combines two piles of the same column.

None of this needs the libraries to agree on anything. Libraries that can still pass tables to one another come to show the same count among themselves, even if the roads to the rest are cut, and when the roads open the rest join them. Any number of libraries can fall silent without stopping the others.

Proof · that the state-based counter is a CvRDT, and that every pair of replicas converges

The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is the entry-by-entry maximum. A CvRDT is an object whose states form a semilattice under an order ≤, whose merge ⊔ is the least upper bound, and whose updates never decrease the state. Claim. This counter is a CvRDT, and any two replicas that keep exchanging states converge.

  1. This is Specification 6 of the comprehensive report (the G-Counter). The payload is a vector P of n naturals, one entry per replica. The update increment at replica g sets P[g] := P[g] + 1; the query value returns Σi P[i]; the merge of X and Y is Z with Z.P[i] = max(X.P[i], Y.P[i]) for each i.
  2. The order is X ≤ Y ⇔ ∀i, X.P[i] ≤ Y.P[i]. Componentwise maximum is the least upper bound of two vectors under this order, since it is an upper bound of both and any other upper bound is at least as large in every entry. So the states form a semilattice, and merge is its join.
  3. Each update increases one entry and leaves the rest, so the state never decreases: s ≤ s • increment. The object is a monotonic semilattice, hence a CvRDT (Theorem 1 of the short paper).
  4. Now let xi and xj be any two replicas that can exchange states infinitely often by some channel that eventually delivers (Proposition 2.1 of the report). Let xi′ = xi ⊔ xj and xj′ = xj ⊔ xi. By the commutativity of ⊔, xi′ = xj′, and by idempotence and associativity further merges of the same states change nothing. Both replicas have the same causal history, C(xi) ∪ C(xj), and the same state.
  5. The report states two assumptions of this vector form: the payload does not overflow, and the set of replicas is known. A grow-only set of unique tags, one per increment, can serve as the same counter without knowing the replicas.∎
What a courier carries

Sending the table or the change

A library can send its whole table, or it can send a short notice of each change: one more scroll lent at library 1. The first is the table way and the second the notice way.

Both can keep every library's count the same. They ask very different things of the couriers.

Library 1 has one more loan to report send it either way, as often as you like

1scrolls lent0shown at library 2

Library 2 has not heard yet.

What the table way asks

Almost nothing

A table may arrive twice, late, or before an older one, and it makes no difference. A courier may be lost and nobody need know, provided some later table gets through. The cost is size: every table, to carry a handful of changes.

What the notice way asks

Exactly once, in order

A notice taken in twice counts twice, and a notice lost leaves a pile short for good. Notices that depend on one another must arrive in that order: a strike must not arrive before the addition it strikes. That needs no vote and no leader, but it is a promise about the roads.

Each is the other in disguise

A table as a notice, notices in a table

A library can send a whole table as a notice, take this table in. And a library can keep in its table every notice it has received and every one it has acted on, so that merging tables merges the notices. The paper proves it both ways.

Proof · that every SEC state-based object can be emulated by an op-based one, and conversely

SEC is strong eventual consistency. A state-based object, a CvRDT, is (S, ≤, s0, q, u, m): states, their order, the initial state, query, update and merge. An operation-based object, a CmRDT, is (S, s0, q, t, u, P): states, initial state, query, prepare-update, effect-update and delivery precondition. Claim. Each can emulate the other.

  1. This is Theorems 3 and 4 of the short paper (§3.2).
  2. State-based by op-based. Given a CvRDT (S, ≤, s0, q, u, m), define a CmRDT with the same state and query. Its prepare-update t(a) records s′ = s • u(a) and its effect-update u′(s′) is s • m(s′), delivered to every replica with no precondition. Merge always commutes, so these effect-updates commute, and with reliable delivery the object is a CmRDT.
  3. Op-based by state-based. Given a CmRDT (S, s0, q, t, u, P), take the state (sm, M, D), where sm is the CmRDT's state and M, D are add-only sets of the updates known and the updates delivered. Order (sm, M, D) ≤ (sm′, M′, D′) by M ⊆ M′ ∧ D ⊆ D′.
  4. A local update runs t and u and adds the update to M. A recursive function d delivers any known update in M \ D whose precondition P holds, adds it to D and applies it to sm, until none is enabled. The merge takes the union of the M sets, then runs d.
  5. Every update is delivered exactly once to the embedded object, in an order satisfying P, and the triple forms a monotonic semilattice (the merge is a union, hence a least upper bound). So the emulation is a CvRDT, and it is SEC because the embedded CmRDT is.∎

So a count that can be kept one way can be kept the other, and the choice is about the roads and the cost.

A count that goes down

Lent and returned

Taking the larger pile works because a pile never shrinks. But the scholar brings scrolls back, at any library, not only the one that lent them. A librarian who took a pebble out would be undone at the next meeting, by any table that still had the larger pile, and the pebble for a scroll another library lent sits in a column no one else may touch.

So the boards keep a second kind of pebble. White pebbles stand for scrolls lent, and black for scrolls returned. Each library has a white column and a black column on every board, and a librarian adds only to the library's own column of each: a black pebble for every scroll brought back to that desk, whichever library lent it.

Each set merges by the larger pile in every column. The number he has out is the white pebbles less the black. Both sets only grow, so both merge safely, and their difference can fall.

Now the deposit sets a limit: it lets him have only so many scrolls out at once. Every desk can read from its own table how many he has out. Is that enough to keep him within the limit?

Room for one more scroll, two desks each sees the room on its own table

A desk may lend

His deposit lets him have three scrolls out. Library 1 and Library 2 have each lent him one, and both tables show two out.

The first thing the idea cannot do

A limit on the whole coast's count cannot be kept from any one library's table

If each desk lends whenever its table shows room, two desks can lend the last room at the same moment, and when their tables meet he has more out than his deposit allows. One cure is to agree before every loan, which is to wait. The other is escrow: split the deposit among the libraries beforehand, and let each desk lend only up to its own share. What a library has lent, less what has come back to it, never passes its share, and the shares add up to the deposit. That is agreeing in advance; the paper's verdict is that there is no cheaper way.

Corrections that meet

Two hands on one work

A table of corrections holds a work's text with the tally of the edition that wrote it. Two libraries correct the same work, each unaware of the other, and every library must end with one result.

Neither rule below is forced by the idea. Both merge in any order and any number of times, and both leave every library with the same result.

The plain rule

Keep the later

The edition with the larger tally wins and the other is thrown away.* It is the larger pile again, applied to a number that only rises. The loser is lost for good. Nothing says the later edition was the better, only that it is later.

What it needs

Tallies that follow events

An edition written by someone who had seen another must carry a larger tally than the one it answers, or the rule would throw away the answer and keep the question.

The other rule

Keep both

Each edition is kept with a note of which editions it was written after, and is dropped only when some kept edition was written after it. Two corrections written in ignorance of each other are both kept, and the reader chooses.

The paper lists several such choices for one kind of record, each a different meaning for the same clash, and all of them settle. What the idea guarantees is that every library settles the same way. It does not say the way is the right one.

A list of titles

Titles added and struck

The libraries also keep a list of the titles of the works on the coast. The simplest list is only ever added to. Two such lists merge by joining their titles, and joining is the same either way round, in any grouping, and twice over. That is the catalogue of titles.

Striking a title off is harder. Three ways follow, and each gives a different meaning to the same clash.

The cheap way

A struck-off list

Keep a second list, the struck-off list. A title is on the catalogue if it is on the first list and not on the second. Both lists only grow, so both merge. A title once struck can never come back: a strike beats an add, for good.

The way most like an ordinary list

A tag for every writing

Each time a title is written, it gets a tag that nobody else will ever use. A title is on the catalogue if any tag of it is. To strike a title, a library strikes all the tags in sight, and only those.

Other ways

A tally, or a count

Each title can carry a tally, so that the later of its last add and last strike wins. Or a count, up with adds and down with strikes, which settles but behaves oddly: a title struck twice needs two adds to return.

One title, two libraries, a tag for every writing add and strike in any order, then let the two exchange

Each library sees only its own list until the two exchange.

A strike takes away only the tags it has seen

An add and a strike made in ignorance of each other leave the add standing

If one library strikes a title while another writes it again, the new writing carries a tag the striker never saw, so the title stays. A title added after a strike is on the catalogue. The paper names this list after what it does: a strike removes what it has observed.

Something different in kind

Not the same as one order

An ordinary list is kept with every act in one order that every library shares. Such a list is simple to reason about, and it asks the libraries to settle that order between them, which means everyone waits.

The lists of titles can give a result that no single order could. Library 1 adds title E and then strikes title F. At the same time, Library 2 adds title F and then strikes title E. Library 3 takes in both.

Four acts, no single order three libraries, later moments further out

    Neither contains the other

    Each kind of promise allows results the other does not

    If the libraries did settle one order they would all end with the same list, so they would agree too. But settling one order needs agreement, and agreement cannot be had if many libraries may fall silent. Here a library is always free to read and to add, whatever the roads, with all but one of the libraries silent.

    Proof · that SEC and sequential consistency are incomparable

    SEC is strong eventual consistency: replicas that have delivered the same updates have the same state. Sequential consistency asks that the result be that of all updates executed in some single order. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), where ∥ means concurrent, e ∈ S. Claim. Neither property implies the other.

    1. This is §3.3 of the short paper. SEC does not imply sequential consistency. Take a Set CRDT with add-wins semantics: after add(e) ∥ remove(e), e ∈ S. Let replica p0 execute add(e); remove(e′), and concurrently replica p1 execute add(e′); remove(e), and let p3 merge both.
    2. Each remove acts on the add it observed at its own replica, and concurrent with the other replica's add, so by the add-wins specification the final state at p3 satisfies e ∈ S ∧ e′ ∈ S.
    3. In any sequentially consistent execution of the four updates in a single order, either remove(e) or remove(e′) is last, and that element is not in S. So the final state above occurs in no sequentially consistent execution.
    4. Sequential consistency does not imply SEC. In the absence of crashes a sequentially consistent object is SEC, since there is a single order after which all replicas terminate in the same state. In general, however, sequential consistency requires consensus, which cannot be solved in the presence of n − 1 crashes, whereas a SEC object is available and converges with up to n − 1 crashes. Therefore the two are incomparable.∎
    The limits

    What it does not say

    The libraries get a count and a catalogue that can always be read and written, that never wait on a courier, and that settle by merging alone. Five things they do not get.

    Does it keep a limit?

    No. Never more scrolls out than the deposit allows, or a catalogue that must never hold two titles together, is a rule about the whole coast, and no library can see the whole coast from its own table. Keeping such a rule means agreeing, beforehand or at times.

    Does it say which result is right?

    No. Every library settles the same way, and the way is chosen by whoever designs the list: the strike may beat the add or the add the strike, the later correction may win or both be kept. Any of them may be reasonable for some use.

    Does it keep the tables small?

    Not by itself. The struck-off list only grows, every tag stays until it is struck, and there is a column for every library. To throw old notices away a library must know every other has taken them in, which it can learn only while no library is silent.

    What does it assume?

    That no librarian lies: one who adds to another's column, or reuses someone's tag, can break it. That the libraries are known and the piles never outgrow their grooves. That on the notice way each notice arrives exactly once, in order of dependence. That tallies follow the order of events.

    Is the list of examples complete?

    No. The paper also gives designs for cross-references between works and for ordered sequences, which are left to the paper. What it shows is the shape of the idea: the merge must take the least that holds both, and changes must only go up, or else they must not mind their order.

    Replicas that only ever move their state upward, and merge by taking the least state that holds both, converge without coordinating.

    A rule that spans all the replicas, such as a count that never goes below zero, still needs agreement.

    The paper behind this book

    Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, Conflict-free Replicated Data Types. Stabilization, Safety, and Security of Distributed Systems (SSS), 2011. — Strong eventual consistency, the state-based and operation-based sufficient conditions, their equivalence, the incomparability with sequential consistency, counters, sets and graphs.

    Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, A Comprehensive Study of Convergent and Commutative Replicated Data Types. INRIA Research Report RR-7506, January 2011. — The portfolio: counters, registers, sets, graphs, sequences, with specifications and proofs.

    The ideas, plainly.

    Shapiro and co-authors ask when replicas of some data can accept changes without ever talking to one another first, and still end the same. Their answer, strong eventual consistency, asks only that replicas that have received the same updates are in the same state. They give two sufficient conditions. In the state-based form the states are ordered so that each update moves a state upward and merging two states is their least upper bound; then merging commutes, groups freely and may be repeated. In the operation-based form every pair of concurrent operations commutes and operations are delivered once each, in causal order. Each form can imitate the other.

    A counter that only counts up is a vector with one entry per replica and a per-entry maximum for merge; a counter that also counts down is two of them. A register can keep the later write or keep both. A set that only grows is a union; a set that also loses elements can let removal win, or let adds win by tagging every add and having a removal take away only the tags it has seen. These all converge, and each means something different by a clash.

    What the approach does not do is keep a rule that spans all the replicas, such as a count that never goes below zero; for that, replicas must agree. It does not decide which meaning of a clash is right, and it is not the same as keeping one order of all the updates: it permits results no single order would give, and it is available where one order would need agreement.

    The papers have four authors, Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, and all are credited here. No one in the book is named: the libraries go by number, and the scholar is the one who lodged the deposit.
